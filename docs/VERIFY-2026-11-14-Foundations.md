# 基礎設計・実装の検証（3D エフェクトビューア）— 2026-11-14

対象: `EffectTest`（`feature/schedule` / commit `de9a238` 時点）
方法: ①全モジュールのコード読解 ②実行テスト（ゴールデン / 決定論 / 異常系 / 性能）
③既存設計書・解析書との突合

---

## 0. 総評

**「データ → VM → 描画」の骨格は成立している。** 境界検査・決定論・ヘッドレス検証・
ゴールデン一元化は水準以上。一方で **CLI 契約（未知引数）と検証条件（ループ）が緩く、
3D の正しさを保証する仕組みが弱い**。直近の `de9a238` で最大の実害（VM の引数オーバーリード）は解消。

| 領域 | 判定 | 要点 |
|---|---|---|
| データ層（`Dat` / `Effect`） | **A-** | 全アクセスが `InRange`/`At` 経由。チャンク走査は終端・破損サイズを捨てる |
| VM（`EffectVm`） | **B**（修正後） | 命令長・引数・dest・キー表に境界あり。引数オーバーリードは修正済み。未実装 op は無言 no-op |
| 座標系・カメラ | **B** | `--camera ffxi` で ffxitool5 と一致。ビルボード軸は手計算で二重管理 |
| 描画（`Gfx`） | **B-** | 6 頂点生成・ZWrite off・CULL none・3 ブレンド。深度ソート・バッチ・デバイスロスト無し |
| CLI（`App`） | **C+** | 終了コード 2/3/4 は定義済み。**未知フラグを黙って位置引数として消費** |
| 検証系 | **B-** | ゴールデン文書＋`ShotStats` はあるが**自動ランナー無し**。ループ条件が未固定 |
| 文書 | **A-** | `GOLDEN.md` / `ANALYSIS-*` / `CAPABILITIES` が実装と対応 |

## 1. 成立している基礎（評価できる点）

1. **層分離が明確**: `Dat`（ファイル/チャンク） → `Effect`（索引・タイムライン・サブ）
   → `EffectVm`（VM#1/#2） → `Gfx`（D3D11 最小層） → `App`（CLI/GUI）。
   描画側は `GfxDrawQuad(center, axisR, axisU, rgba, uv, srv)` の 1 API に集約され、
   ワールド座標で完結している（= 座標系の変更点が 1 箇所で済む構造）。
2. **データ境界検査が全域**: `DatFile::At/InRange` を必ず経由し、
   `Dat.cpp:37`（`next < 16` 終端 / `pos + next > Size()` 破棄）、
   キー表評価も `InRange(e, 8)` で毎回ガード（`EffectVm.cpp:33,71,86,95,131,144`）。
3. **暴走ガード**: VM ループ 8192 命令、入れ子 Schedule 16 本、サブタイムライン 1024 命令。
4. **決定論**: `srand(1)`（`App.cpp:1358`）＋固定 dt（1/60）＋`Present` 無しの描画。
   同一コマンド 2 回で **PNG の SHA-256 が一致**（実測）。
5. **ヘッドレス検証**: `--list / --base / --action / --selftest / --shot` が出揃い、
   画素は `tools/ShotStats.ps1`、形状は `tools/RingStats.ps1` で数値化できる。
6. **ゴールデンの一元化**: `docs/GOLDEN.md` を唯一の正とし、他文書の旧値を明示的に無効化。

## 2. 不備（重要度順）

### 2.1 高 — 3D の正しさ（**修正済み** `de9a238`）

- **症状**: Cure `tgt0` の `kr10` が `z = -41 m` まで流れる（0.5 m/フレーム）。
- **原因**: `arg` を `p+4` の配列として **命令長を無視して `arg[0..2]`** 読んでいた。
  `op=0x08 len=2`（引数 1 個）の `arg[2]` が次命令 `op=0x72` の arg0（-0.5）を拾い、
  VM#2 `0x02`（len=1・引数なし = `Pos += Dest`）が毎フレーム積んでいた。
- **修正**: 引数を `len-1` 個に制限（`argBuf[12]`）、キー名は `len>=3` のみ。
- **結果**: `kr10` の z は **-0.148 で一定**、x は `-0.005/フレーム`（データどおり）。
  既定ゴールデンは更新（`11\17`=10,343/204、`11\18`=3,948/454、`11\22`=970/303、`12\43`=4,661/263）。

### 2.2 高 — 検証条件が固定されていない（ループ）

- `m_Loop = true` が既定（`Effect.h:421`）で、**`--loop` の CLI が無い**。
  そのため `--frames N` が duration を超えると**周回する**。
  例: Cure `tgt0` は 239 フレーム。`--frames 260` は 1 周して 21 フレーム目を撮っている。
- 影響: ゴールデンの「どの時点の絵か」が暗黙になり、比較が再現しない恐れ。
- 推奨: `--loop on|off` を追加し、**`--shot` の既定を off**。GOLDEN の条件に明記。

### 2.3 中 — CLI 契約（未知引数・暗黙フォールバック）

- **未知フラグが黙って位置引数になる**（`App.cpp:2164`
  `else strncpy_s(png, tok, _TRUNCATE);`）。
  実測: `--bogus 1` を付けると **exit=0** のまま `1` という PNG が生成された
  （＝タイポが「無効化」ではなく「出力先の変更」になる）。
- **`--action <未知名>` が main を黙ってダンプ**（`Effect.cpp:516`
  `if (mainChunk == nullptr) mainChunk = dat.FindByType(0x07);`）。実測 exit=0。
  `--sched` だけは 2026-11-14 に厳密化済み。
- 推奨: `--` で始まる未知名は **exit 2**。`--action` は名前一致必須（`--sched` と同様）。
- 参考: 終了コードは `2`=usage / `3`=DAT 読込失敗 / `4`=timeline 無し **または PNG 保存失敗**
  （`return ok ? 0 : 4;`）で、`4` が 2 つの意味を持つ。

### 2.4 中 — 描画パイプライン

| 項目 | 現状 | 影響 / 推奨 |
|---|---|---|
| 深度ソート | **無し**（描画順 = インスタンス順） | 既定 `alpha_add` は順序非依存で回避。`--blend alpha` / `auto` では破綻。α モード時は距離ソートを |
| バッチ | **1 サブ = 1 Draw(6)** | Cure `tgt0` f200 で **430 サブ/フレーム**。現規模は問題ないが粒子数に線形 |
| ゲイン | PS に **1.5 固定**（`Gfx.cpp:64`）＋ App 側で `g_Gain/1.5` 補正（`App.cpp:770`） | 二重管理。ゲインは定数バッファに載せるべき |
| 白フォールバック | `Gfx.cpp:395` は `srv==nullptr` を白で描くが、`App.cpp:536` で**先にスキップ** | 方針が二重。どちらか 1 箇所に統一 |
| Z | `DepthWriteMask=ZERO`（`Gfx.cpp:186`）/ `LESS_EQUAL` | 加算前提として妥当。α 合成時は ZWrite 必要可否を再検討 |
| デバイスロスト | 未処理 | 長時間実行・解像度変更で復帰不能になり得る |

### 2.5 低 — 座標系の一貫性

- **ビルボード軸を yaw/pitch から手計算**（`App.cpp:499`）し、`ffxi` モードでは定数
  （右=-X / 上=+Y）に差し替えている。カメラを増やすと再発する。
  → 推奨: **view 行列の逆行列**から right/up を導出（1 箇所で整合）。
- **`--zup` はビルボード中心のみ**変換（`App.cpp:568`）。`0x1F` のローカル頂点
  （`gq.ctr` / `gq.aR/aU`）は変換されないため、`--zup on` では 0x1F だけ別空間になる。
  （実験フラグなので実害は限定的だが、組み合わせの意味が不明確）
- 骨行列は「中心のみ」適用（ビルボード軸は回さない）— 意図と根拠がコメント済みで妥当。

### 2.6 低 — リソース初期化

- `GfxInit` は途中失敗時に生成済みリソースを解放せず `false` を返す（呼び出し側は
  `GfxShutdown` を呼ばない）。失敗経路の後始末を 1 箇所に集約したい。
- テクスチャ索引は**生成失敗でも index を揃える**設計（`Effect.cpp` の `BuildTextures`）で、
  `m_TexNames` と `m_Textures` の対応が崩れない点は良い。

## 3. 検証系の弱点

1. **自動ランナーが無い**。`docs/GOLDEN.md` は「文書」で、CI/スクリプトによる照合が無い。
   現状は手作業で `--shot` → `ShotStats.ps1` → 目視比較。
2. **異常系の期待値が未文書**。終了コードの意味（2/3/4）と、
   「未知フラグはエラー」などの契約が決まっていない。
3. **`--shot` の条件が散在**。`--loop` が無く、`--frames` と duration の関係が
   ゴールデンに書かれていない（§2.2）。

提案（小さい順）:

- `tools/Verify-All.ps1`：4 DAT ＋ Cure `tgt0` ＋ `--selftest` ＋ 決定論（2 回実行の SHA 一致）を
  一括実行し、`docs/GOLDEN.md` の値と**自動照合**する。
- CI（GitHub Actions / Windows ランナー）で `--selftest` だけでも回す。
  GPU が要る `--shot` は手元実行＋レポート添付とする。

## 5. 推奨アクション（優先順）

| # | 内容 | 理由 | 規模 |
|---|---|---|---|
| 1 | `--loop on\|off` を追加し、`--shot` は既定 off | ゴールデンの時点を固定できる | 小 |
| 2 | 未知フラグ（`--xxx`）と未知 `--action` を **exit 2/4** に | タイポの黙殺を止める（検証の信頼性） | 小 |
| 3 | `tools/Verify-All.ps1`（GOLDEN 自動照合） | 回帰を人手に依存しない | 小 |
| 4 | ビルボード軸を view 行列から導出 | `--camera` 追加時の不整合を根絶 | 小 |
| 5 | α 合成時の深度ソート（または `alpha_add` 固定の明記） | `--blend alpha` の破綻を防ぐ | 中 |
| 6 | ゲインを定数バッファへ / 白フォールバックの一本化 | 二重管理の解消 | 中 |
| 7 | デバイスロスト・`GfxInit` 失敗時の後始末 | 長時間実行の安定性 | 中 |

## 6. まとめ

- **基礎は成立**：データ境界・VM の実行モデル・描画 API・決定論・ヘッドレス検証が揃っている。
- **最大の実害は解消済み**：VM の引数オーバーリード（3D 座標の破壊）は `de9a238` で修正。
- **残る本質的な弱点は「検証の固定」**：ループ条件・CLI 契約・自動照合の 3 点（推奨 1〜3）。
  ここを入れると、今後の ffxitool5/AltanaView 追い込みで**回帰事故を機械的に防げる**。
