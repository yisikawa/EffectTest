# インスタンス毎の骨指定（調査メモ / 2026-11-09）

> 対象: `0x07` の `0x02`/`0x03` で生成される 1 枚のビルボード（= インスタンス）を、
> **どの骨の座標系に載せるか**という設計課題。現状は「エフェクト全体で 1 本の骨」だけ。

## 1. 用語と現状の実装

| 用語 | 意味 |
|---|---|
| インスタンス | `EffectContext::Spawn()` が作る `MotionInstance`。1 枚の板。位置・拡大・色・UV を VM が決める |
| ルート変換 | インスタンスの `center` / `axisR` / `axisU` に掛ける 4x4。現在は `--bone N` で**全インスタンス共通に 1 本** |

```
[効果 DAT の VM] → instance.pos / scale / color / uv
                        ↓
              （ここに骨行列を掛けたい）
                        ↓
                 GfxDrawQuad(...)
```

現状（`--shot --bone N`）は**全インスタンスに同じ骨行列**を掛けるだけ。したがって
「手に付く炎」と「足元の煙」を分けることができない。

実測（`11\18` Fire II / 90 フレーム、human 基準）:

| 条件 | 非背景 |
|---|---|
| 骨なし（既定） | 2,694 |
| `--bone 0`（根） | 452 |
| `--bone 10` | 452 |

## 2. なぜ必要か（参照動画の観察）

`fire2.mp4`（Target=NPC）の 6.2 s には**性格の違う 3 層**が同時に出る。

| 層 | 見え方 | 付くべき場所（推定） |
|---|---|---|
| 炎 | 腕・脚に沿った細い炎 | 各部位の骨（腕/脚） |
| 赤い光点 | 胸元の小さな発光 | 胸部の骨 |
| 煙 | 体の左上へ流れる黒煙 | 体の中心〜頭 |

1 本のルートでは「全部が同じ位置・同じ向き」になり、この 3 層を再現できない。

## 3. 情報源の棚卸し（何が分かっていて、何が無いか）

| 候補 | 実測・確認結果 | 使えるか |
|---|---|---|
| **骨名** | 参照実装 `CBone::LoadBone` は `SetName(Name)` に**空のローカルバッファ**を渡す（`Model_Anim.cpp:136-147`）。`m_Name` は実質空 | ❌ **名前では引けない** |
| **エフェクト DAT の骨** | `11\17`/`11\18`/`11\22`/`12\43`/`162\50` に `0x29`/`0x2A`/`0x2B` は **0 件** | ❌ 効果側に骨情報なし |
| **generator ヘッダ（`0x05`）** | 候補は `+0x11` のみ。`11\18` では `g007` だけ `0x04`（id=0x0402）、他は `0x00`（id=0x0002）。`+0x90` 以降は VM ペイロード、`+0xAC` はリンク名 | △ 決め手なし（`+0x11` が骨 index の可能性は残る） |
| **timeline op** | `0x02` の `param` は生成時刻（秒×60）。他に骨 index らしき値は未発見 | △ 未確定 |
| **VM op（VM#2）** | `0x25` = サブオブジェクト 0x42 dword を子へ複製、`0x33`/`0x46` → `FUN_0040f8b0`、`0x45` = 親ボーン合成（我々は平行移動で近似） | △ `FUN_0040f8b0` を解析した結果**骨解決ではない**（下記） |
| **モデルの Schedule（`0x07`）** | `atk0` は `0x03 name=hwat`（= `0x2B` モーション名）/ `0x57 name=vatk`（入れ子）のみ。骨名は出ない | ❌ 骨指定なし |

## 4. `FUN_0040f8b0` の解析結果（2026-11-09）

`op 0x33` / `0x46` から呼ばれる関数を decompile した結果:

- 引数は `(effectRoot, float* outMatrix)`
- `in_EAX + 0x8c / 0x90 / 0x94` の **3 つの角度**から `cos/sin` で回転行列を作り、
  `param_2 + 0xc/0xd/0xe`（行列の `_41,_42,_43`）へ並進を書き込む
- 途中で `effectRoot + 0x1a8`（フラグ）と `+0x1d0`（軸方向のバイアス量）を参照

→ **「サブオブジェクトの角度から行列を合成する」処理**であり、**骨の検索は行っていない**。
したがって「どの骨に付くか」は効果側のコードでは決まらず、**呼び出し側（app）が effect root に
骨行列を渡している**と推測される（その結線は未観測）。

## 5. 実現案（4 つ）

### A. データ由来の骨 index を使う（本命）
- **前提**: どこかに bone index がある（`0x05 +0x11`、`0x02 param`、`0x19` キー表、`0x3D` パラメータ）
- **利点**: データが正で、任意の DAT に自動適用できる
- **欠点**: 現時点で**該当フィールドを特定できていない**
- **必要な作業**: `+0x11` の分布調査（全効果 DAT で 0..93 に収まるか）、`0x3D` の内容解析

### B. 呼び出し側（モデル側）の規則に従う（本命の代替）
- **前提**: AltanaView の effect root がモデルの骨を受け取る経路がある（`0x25`/`0x33`/`0x45`/`0x46`）
- **利点**: 「どの骨に付くか」はモデル側の設定なので、効果 DAT を汚さない
- **欠点**: **モデルの Schedule 側に骨指定が無い**ため、AltanaView 側の規則（op の意味）を解明する必要
- **必要な作業**: `FUN_0040f8b0` の decompile、`0x45` の対象（`puVar9[0x20..]` か別オブジェクトか）の確認

### C. 名前/系統によるヒューリスティック
- 例: `kemuri*`（煙）→ 体の中心、`fir*`（炎）→ 胸部、`dist` → 距離指定
- **利点**: すぐ実装でき、見た目が近づく可能性
- **欠点**: **根拠が無い**（推測）。別の DAT で破綻する。設計方針として採用したくない
- **位置づけ**: 検証用の暫定に限定（既定にはしない）

### D. 現状維持（全体で 1 本）
- **利点**: ゴールデンが安定。実装済み
- **欠点**: 参照の 3 層構造を再現できない

## 6. 推奨手順

1. **B の解明**（最優先・1 時間規模）: `FUN_0040f8b0` と `0x45` の decompile。effect root が骨行列をどう受け取るか
2. **A の分布調査**: 全効果 DAT の `0x05 +0x11` を集計し、値域が「ボーン数以下」かを確認（`0x04` のような小さい値が骨 index か）
3. 決まったら `MotionInstance::boneIndex` を追加し、`--bone` を「全インスタンス既定」に、`--bone-map`（`インスタンス index:bone`）を検証用に追加
4. **C は既定にしない**（検証の暫定フラグに留める）

## 7. 決まったときの実装形（案）

```cpp
struct MotionInstance {
    int boneIndex = -1;      // -1 = ルート（従来）
    ...
};
// Spawn 時: mi.boneIndex = ResolveBoneIndex(g, op);   // A か B の規則
// 描画時:
const float* M = (mi.boneIndex >= 0) ? skel.World(mi.boneIndex) : rootXform;
```

検証は `--shot --model human --motion <name> --frames N` の画素と、
参照動画（`fire2.mp4` の 4.2 s / 6.2 s）との**層ごとの位置比較**で行う。
