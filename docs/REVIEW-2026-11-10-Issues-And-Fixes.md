## 2. 問題 1【高】キーフレーム表の参照を誤解している

### 2.1 現状

- VM#1 は、op `(0x20<op<0x30) | (0x32<op<0x37) | (0x58<op<0x5C)` のとき、命令の 3 番目の dword を `su.keyOff[dest]` に保存する（`EffectVm.cpp:113-118`）。
- VM#2 の op `0x0F..0x21` は、`keyOff[dest]` を**ファイル先頭からのオフセット**として `EvalKeyTrack` に渡す（`:403-409`）。
- `EvalKeyTrack` は `InRange` に失敗すると `0.0f` を返す（`:24`）。呼び出し側はその結果を `outSlot[0]` に毎フレーム書く（`:409`）。

### 2.2 根拠（実データ）

3 つの DAT で、上記 VM#1 のキー op の第 3 dword を調べた。

| DAT | キー op 数 | 4 文字 ASCII | 既存 `0x19` チャンク名と一致 |
|---|---|---|---|
| `11\17` | 8 | 8 | 8 |
| `11\18` | 9 | 9 | 9 |
| `12\43` | 10 | 10 | 10 |

- **全 27 件が `k006` のような 0x19 チャンクの名前**だった。
- `11\18` の 9 件は、絶対オフセット／チャンク相対オフセットのどちらで読んでも妥当な表にならなかった（妥当 0 件）。
- 0x19 チャンクの構造（`11\18` の `k006` / `k001` ほかで確認）:
  - 先頭 4 バイト = 名前、`+4` の u32 の下位 7 ビット = type（0x19）。
  - `+0x18` から 8 バイト `[time(float), value(float)]` の並び。
  - 例: `k006` = `(0.225,0.42) (0.45,0.42) (1,-0.02)`、`k001` = `(1,1)`、`k002` = `(0.34453,0.5) (1,6.9e-07) (0,0)`。
  - サイズ = `0x18 + 8×n`。

### 2.3 影響

1. `keyOff` に `0x3630306B`（"k006" を u32 として読んだ値）のような**常に非 0 の巨大値**が入る。
2. `EvalKeyTrack` は常に `0.0f` を返す。
3. VM#2 の `0x0F..0x21` が Pos / Move / Scale / Color / UV のスロットを毎フレーム **0 で上書き**する。
4. `--selftest` で `11\17` / `11\18` / `12\43` の主要 generator が **α=0.00**（例: `col=(0.86,0.44,0.24,0.00)`）。
5. コミット `6444148` の「`11\18` 3,051 → 3,236（色/α が変化）」は、補間の成功ではなく**ゼロ書込みの副作用**だった可能性が高い。

### 2.4 修正案

| 項目 | 案 |
|---|---|
| 参照の意味 | `dword2` を **0x19 チャンク名**として扱い、`dat.Find(name, 0x19)` で解決する |
| 表の開始 | `chunk.offset + 0x18` |
| 表の終端 | `chunk.size` で縛る（現状は最大 64 エントリを走査し、次チャンクのバイト列まで読む） |
| 保持方法 | `keyOff[]`（u32 オフセット）をやめ、解決済みの「チャンク参照（offset と件数）」を保持する。名前解決はスポーン時（VM#1 実行時）に 1 回だけ行う |
| 未解決時 | 出力スロットを **書かない**（0 で上書きしない）。`--opstat` と同様に件数を集計してログに出す |
| 外挿 | 先頭キーの時刻が 0 より後（例 `0.225`）のときの扱いを決める（現状は `prevT=t, have=true` で最初のキー値に張り付く）。AltanaView `FUN_0040f820` の挙動を要確認 |
| 末尾の `(0,0)` | `k002` / `k009` のように末尾が `(0,0)` の表がある。パディングか実キーかを AltanaView 側で確認する |

### 2.5 検証

- `--selftest` に **「キー op の名前解決率 = 100%」** を追加（`11\17` / `11\18` / `12\43` で 27/27）。
- 修正前後で α と色が 0 でなくなることを `--selftest` の `frame=59/119/239` 行で比較する。
- ゴールデン（`11\17` / `11\18` / `11\22` / `12\43` の `nonBg` / `maxSum`）は**意図的に更新**し、更新理由を `docs/GOLDEN.md`（#8 参照）に記録する。
- 広域回帰: `11\0-11\19` / `12\0-12\19` の 40/40 成功を維持する。

### 2.6 リスク

- 見た目が大きく変わる（α が出るため）。ゴールデンの更新は避けられない。
- 0x19 の `+0x04..+0x17` の意味（時間スケール等）は未確定。`+0x18` 起点とする根拠は 3 DAT の実測のみ。

## 5. 問題 4【中】毎フレームの深コピー

### 5.1 現状

- `Effect.cpp:662-669`: 毎フレーム `std::vector<MotionInstance> alive` に生存インスタンスを**コピー**して `swap` する。
- `MotionInstance` は `std::vector<SubUnit>` を持ち、`SubUnit` は `SubObject`（約 520 B）と `keyOff[64]`（256 B）などを含む。
- 粒子 512 個 × 十数インスタンスなら数 MB/フレームのコピーになり得る。
- 期限切れが 0 件のフレームでもコピーする。

### 5.2 修正案

- 期限切れが 1 件以上あるときだけ、`erase(remove_if(...))` で詰める。
- 問題 1 の修正で `keyOff[64]` が小さな参照に置き換われば、`SubUnit` も小さくなる。

### 5.3 検証

- ゴールデン不変（挙動が変わらない最適化であること）。
- 簡易計測: `--shot --frames 600` の所要時間を修正前後で比較（目標: 悪化しない）。

## 6. 問題 5【低〜中】`SubObject` の範囲外書込み

### 6.1 現状

- `SubObject::f` は 130 float（`(0x108 + 64*4) / 4`）。最大添字は 129。
- VM は `dest < SUB_DEST_N(64)` だけを検査し（`EffectVm.cpp:108, 354`）、`d[0..2]`（色の op は `d[0..3]`）へ書く。
- 計算上、`dest=62, 63` の `d[2]`（添字 130, 131）は**範囲外**。色の op は `dest>=61` で範囲外。
- 現行 DAT の dest は 0〜十数程度のため通常は発火しない。破損 DAT や未知 DAT で問題になる。
- `Effect.h` に `static_assert` は無い。

### 6.2 修正案

- 検査を `dest + 4 <= SUB_DEST_N` に変更する（または配列に余裕を持たせる）。
- `static_assert` で `SUB_DEST_N` と配列サイズの関係を明記する。
- 範囲外 dest を検出したら、`--opstat` と同様にカウントしてログへ出す（黙って無視しない）。

### 6.3 検証

- dest=63 の合成命令を渡しても書込みが発生しないことを確認する（ダミーの DAT バイト列が必要。実装計画で方法を決める）。
- 既存ゴールデン不変。

## 8. 問題 7【中】色/α の「代替」処理と検証方法が不具合を隠す

### 8.1 現状

| 場所 | 内容 |
|---|---|
| `App.cpp:618-623` | RGB が全 0 なら白、α ≤ 0 なら 1 に置換 |
| `App.cpp:549-556` | geo 側にも同様の RGB 置換（α は 0 なら描かない） |

| 検証 | ゴールデンが `nonBg`（画素数）と `maxSum` 中心で、色の正しさを検出しにくい |
| 基準値 | ゴールデンが自分の実装から作られており、バグを含んだ値が基準になる |

3. 検証手段を強化する:
   - 参照フレーム（`frames/v_*.png`）との画素比較（色相・輝度の分布）。
   - `--selftest` で「期待 α/色の範囲」を検査（例: `11\18` の主要 generator が `t01` の途中で α > 0 になる）。
4. `colorSet` フラグ導入は**設計変更**として別途設計書化する（既存メモの方針どおり）。

### 8.3 リスク

- 撤去により一時的に見た目が悪化する。問題 1 とセットで段階的に行い、各段でゴールデンを記録する。
