# AltanaView 0x21（テクスチャフレーム）描画の解析

対象: `AltanaView_unpacked.exe`（SHA-256 `b5494a7c…`, 418,816 B）
※ `AltanaView.exe`（配布物 182,272 B）は **UPX パック**（セグメント `UPX0`/`UPX1`、関数 16 個）で、
そのままでは関数が解決できない。解析は展開版で行う。

---

## 1. 0x21 オブジェクトの構築 `FUN_0040c360`

```c
uVar2   = *(ushort *)(chunk + 0x12);                  // フレーム数
hdr     = (-(*(char *)(chunk + 0x14) != 0) & 0x10) + 4;   // 4 または 0x14
iVar8   = chunk + 0x28;                               // 先頭フレーム
texture = FUN_004059a0(chunk + 0x18, ...);            // ★テクスチャ名は +0x18
for (i = 0; i < uVar2; ++i) {
    cnt   = *(byte *)(iVar8 + 2);                     // 0x90 ブロック数
    tbl[i] = { cnt, iVar8 + hdr };                    // 8 バイト（cnt, データ先頭）
    iVar8  = iVar8 + hdr + cnt * 0x90;                // ★次フレーム
    maxcnt = max(maxcnt, cnt);
}
```

→ **当方の実装（`ParseTexFrames`）と完全一致**（`+0x12` count、`+0x14` で hdr 4/0x14、`+0x28` 起点、stride `cnt*0x90`）。
差分は **テクスチャ名を `+0x18` で解決している**点（当方は `+0x20` の specific 名で解決）。

## 2. 描画 `FUN_0040c4e0`（0x21 の実体）

### 2.1 頂点バッファ

```c
iVar3  = *(int *)(this + 0x18) * param_2;      // 頂点数 × サブ個数
uVar11 = iVar3 * 6;                            // 6 頂点/クワッド
CreateVertexBuffer(uVar11 * 0x18, 0x208, 0x142, ...)   // FVF=0x142 (XYZ|DIFFUSE|TEX1), 24 B
Lock(0, iVar3, &pData, 0);
```

- **1 インスタンス = 6 頂点 = 1 クワッド = 2 三角形**
- 頂点 24 B = `float3 pos` + `D3DCOLOR` + `float2 uv`（＝当方の 24 B 解釈と同じ）
- 終端で `SetFVF(0x142)` → `SetStreamSource(0, vb, 0, 0x18)` → `SetTexture(0, this+8)` →
  **`DrawPrimitive(D3DPT_TRIANGLELIST, 0, サブ個数 * 2)`**

### 2.2 フレーム選択は「乱数」

```c
uVar14 = rand();
iVar10 = frameTbl[uVar14].cnt;          // 毎描画、インスタンスごとに 1 枚を無作為に選ぶ
iVar12 = frameTbl[uVar14].data;
```

→ **時間で進めない**。当方の「経過時間 → フレーム index」は誤り。
（検証用に `--uvframe random|time` を追加。既定 `random`）

### 2.3 色は「閾値つきディザ」＋乗算

```c
cR = sub[0xa4]; cG = sub[0xa8]; cB = sub[0xac]; cA = sub[0xb0];   // 0..1
uR = (cR < 1.0f) ? rand() : 0xff;   // ★1.0 未満なら乱数バイト（ディザ）
...（G, B, A も同様）
vtxColor = FUN_00401f70(packed(cR,cG,cB,cA), quadColor);         // 頂点色を乗算
```

`FUN_00401f70` はチャンネルごとに `(a * b) >> 7`（＝ `a*b*2/255`）。
したがって **クワッド側の `0x80`（128）が中立（1.0）**。当方は 0x21 の頂点色を無視している。

### 2.4 UV は「0x21 の uv ＋ サブのオフセット」

```c
*(float *)(vout + 0x10) = *(float *)(sub + 0xb4) + *(float *)(vsrc + 0x10);   // u
*(float *)(vout + 0x14) = *(float *)(sub + 0xb8) + *(float *)(vsrc + 0x14);   // v
```

→ `sub+0xB4/0xB8` は **UV スクロール**（データ 3 の op `0x26`/`0x28`「テクスチャ座標 u/v の追加変化」）。
当方は未実装（常に 0）。

### 2.5 頂点の変換は行列

```c
iVar3 = sub + 0x40;              // ★サブ内 0x40 の 4x4 行列
thunk_FUN_0042d8dd(dst, iVar3, src);   // 0x21 のローカル座標を行列で変換
```

→ **クワッドは「行列で変換」される**。常にカメラ正対になるのは、この行列が
ビルボード（カメラ基準）として組まれているため（ユーザー指摘のとおり）。
当方は軸ベクトルで直接組んでおり、結果は同じだが**行列経由の方が忠実**。

## 3. 重要な欠落: 1 generator = 複数サブ（粒子）

`MotionObject` は `count = byte@+0x78 + 1` 個の**サブオブジェクト**を持ち、ストライドは `0x108 + count*4`。
VM#1 / VM#2 は **サブごとに**実行される（`FUN_0040e600` のループ）。

実測（`+0x78`）:

| DAT | generator | count | stride |
|---|---|---|---|
| `11\18` / `11\17` | 全部 | **1** | 0x108 |
| `12\43` | `g006` | **12** | 0x134 |
| `12\43` | `g011` / `g010` | 4 | 0x114 |
| `12\43` | `g008` | 2 | 0x10C |
| `162\50` | `csh1` | 3 | 0x110 |

→ **当方は常に 1 サブ**なので、`12\43` の `g006` だけで 11 個分の粒子が欠けている。
`11\18`/`11\17`（Fire 系）は count=1 なので影響なし → **参照動画との差はここではない**。

## 4. 一般実装との対応（WEB 調査）

| 項目 | 一般論 | AltanaView | 当方 |
|---|---|---|---|
| 向き | ビルボードは `CameraRight`/`CameraUp` で四隅を作る（opengl-tutorial "Solution #2"） | サブの 4x4 行列（カメラ基準で構築）で変換 | カメラ right/up で直接（等価） |
| サイズ | `center + right*x*size.x + up*y*size.y` | 0x21 のローカル座標 × 行列（＝メートル） | 同（`--size quad`） |
| アニメ | UV スクロール／フレーム差し替え | **乱数フレーム**＋UV オフセット加算 | 経時フレーム（→ `--uvframe` で乱数化） |
| 色 | 頂点色 × テクスチャ | 頂点色を `×2/255` で乗算＋**閾値ディザ** | インスタンス色のみ |
| 生成数 | エミッタで複数 | `count = +0x78+1` のサブ固定 | 1 固定（→ 未実装） |

FFXI のデータ構造については `cosmosa.jp/ffxitool/generator.html`（2007 年の解析）が一致する情報を持つ:
- ヘッダ 0x70+ バイト、データ 1〜4 へのオフセット
- `bil`（WORD）: **0 = 平面 / 1 = ビルボード**
- データ 2 の op `02h` = 「フレームごとの移動量 dx,dy,dz」→ **速度**
- データ 3 の `26h`/`28h` = 「テクスチャ座標 u/v の追加変化（フレーム単位で加算）」

| 試行 | 結果 | 理由 |
|---|---|---|

> あるため、単独では破綻する」ケース。式と前提をセットで実装するまで既定は従来挙動を維持する。

## 6. フレームレートは 30 か 60 か（2026-11-09 追跡）

### 6.1 時間ステップの生成（`FUN_004012a0` メッセージループ）

```c
local_38 = timeGetTime();                                  // ms
local_34 = (float)(int)(local_38 - DVar2);                 // 前回との差
local_34 = local_34 * _DAT_00452c4c;                       // ← 1/1000（ms→秒）
FUN_00424510(unaff_ESI + 9, &local_34);                    // この dt で 1 フレーム進める
```

- **dt は「実経過秒」で可変**。固定 1/60・1/30 の量子化は無い
- `QueryPerformanceCounter` は別用途（1 箇所のみ）

### 6.2 データ側の「60」は“刻み”の定義

| 箇所 | 式 | 意味 |
|---|---|---|
| タイムライン | `timeLeft += delay * (1.0f/60.0f)` | delay の単位は **1/60 秒** |
| VM#2 | `k = dt * 60.0f`（`_DAT_00452c50`） | データ増分は **1/60 秒あたり** |
| ジェネレータ長 | `length = (u16@+0x76 + 1) / 60` | フレーム数 ÷ **60** |
| 0x21 フレーム | `idx = elapsed * 60` | 60 枚/秒 |

→ **描画 fps は可変、データの時間単位は 60 Hz**。

### 6.3 実データ・参照動画による裏取り

- `11\17` の `g006` は `+0x76 = 200` → **201/60 = 3.35 s**
- `fire2.mp4` 実測: 開始 3.2 s、終了まで約 4.1 s → 60 Hz 解釈と整合
  （**30 Hz なら 6.7 s** になり動画と合わない）

### 6.4 当方への影響

- `--shot --frames N` は 1 フレーム = **1/60 秒**で進めており、**この解釈で正しい**
- AltanaView は可変 dt だがデータ基準が 60 Hz のため、固定 1/60 でも同じ時間発展になる
- **fps に起因する修正は不要**

## 8. 付属情報（bone/位置/継続時間）の出どころ — `FUN_0040d790` の op 0x01

`FUN_0040d790`（EffectRoot 構築）はストリーム B を走査し、**op 0x01 の命令フィールド**から
ルートの付属情報を取り出す:

```c
bVar14 = *pbVar3;                       // op
if (bVar14 == 1) {                      // ★ op 0x01 = 付属情報ブロック
    iVar11 = *(int *)(pbVar3 + 0x0c);                    // ID（'dist' など 4 文字）
    bVar14 = pbVar3[0x21];                               // 資源タイプ（0x22/0x0B→0x1F/0x0E→0x21/0x1D→0x25/0x24→ring）
    *(u32 *)(param_1 + 0x1a8) = *(u32 *)(pbVar3 + 0x04); // ★フラグ + bone index（&0xf / >>4 / >>10 で解釈）
    *(u32 *)(param_1 + 0x1ac) = *(u32 *)(pbVar3 + 0x14); // ★位置 X
    *(u32 *)(param_1 + 0x1b0) = *(u32 *)(pbVar3 + 0x18); // ★位置 Y
    *(u32 *)(param_1 + 0x1b4) = *(u32 *)(pbVar3 + 0x1c); // ★位置 Z
    ...
    uVar13 = *(u32 *)(pbVar3 + 0x20) & 0xff;             // ★サブ個数（+0x1c0）
    local_54 = *(u32 *)(pbVar3 + 0x20) >> 16;            // ★継続時間[フレーム]（+0x1c8 = n/60）
    *(u32 *)(param_1 + 0x1bc) = uVar13 + 0x108;          // ストライド
}
```

さらに骨 index の解釈（10796-10805）:

```c
if (param_1[0x5d] == 0 && *(int *)(param_1 + 0x1a0) == 0) {
    uVar13 = *(uint *)(param_1 + 0x48);
    if ((uVar13 & 3) == 1) uVar13 >>= 4;      // ★ bone index（下位ニブルが 1 の形式）
    else                   uVar13 >>= 10;     // ★ それ以外の形式
```

### 8.1 当方への含意

- **bone index は「データ中の op 0x01 命令」に存在する**（`+0x04` → `+0x1a8`）
- 併せて **サブ個数**（`+0x20 & 0xff`）と**継続時間**（`+0x20 >> 16`）も同命令から決まる
- 当方はサブ個数を `generator+0x78`、継続時間をタイムライン delay 合計から求めているため、
  **この op 0x01 ブロックを読む実装に置き換えれば、bone/個数/継続時間が一度に揃う**

### 8.2 実測: op 0x01 は**今回の DAT 群では見つからなかった**

`11\18` / `11\17` / `11\22` / `12\43` / `162\50`（効果 DAT）と `131\6` / `27\82`（モデル DAT）について、
`+0x84`（ストリーム B）と `+0x8C`（ストリーム D）を走査したが **op 0x01 は 0 件**。

| 対象 | 走査範囲 | op 0x01 |
|---|---|---|
| 効果 DAT の `0x05`（generator） | `+0x84` / `+0x8C` | **なし** |
| 効果 DAT の `0x07`（main） | `+0x84` / `+0x8C` | **なし** |
| モデル DAT の `0x05`（モーション） | `+0x84` / `+0x8C` | **なし** |

→ `FUN_0040d790` が構築するオブジェクトは、**0x05/0x07 チャンクではない別の型**
　（例: モデルのアクション／エフェクト起動コマンド）である可能性が高い。
　 次は「どのチャンク型が `FUN_0040d790` に渡されるか」を、その呼び出し元（vtable 経由）から特定する必要がある。

### 8.3 現時点の結論

- bone index（`+0x48` → `&3==1 ? >>4 : >>10`）と付属位置（`+0x1ac..+0x1b4`）、
  サブ個数・継続時間（`+0x20` の word）は **op 0x01 ブロック**から来る（実装は確定）

- 当面は `--bone-map` で近似（§7.3 の実測どおり、体軸方向の分散は再現できる）

## 10. `0x1F`（ジオメトリ）の構造 — 実測で判明

`FUN_0040b9d0`（0x1F オブジェクト生成）と実データ（`11\17` `f101` 0xDB0、`11\18` `fire` 0x110）から:

```c
uVar7    = *(byte *)(chunk + 0x14);      // ★4 文字名の個数
puVar8   = (ushort *)(chunk + 0x18);     // u16 配列（先頭要素 = 総数）
piVar4[2]= *(ushort *)(chunk + 0x16);    // 配列の先頭値（要素数）
FUN_00421720(piVar4 + 3);                // 配列を確保
for (i = 0; i < len; ++i) tbl[i] = puVar8[i];      // u16 をコピー
// その後: (byte)puVar8 が 0x1F<x<0x7F の「4 文字名」ペアを 16 バイト間隔で走査し、
//         FUN_004059a0 で名前 → チャンク解決（uVar7 個）
```

| オフセット | 内容 | 実測（`fire`） | 実測（`f101`） |
|---|---|---|---|
| `+0x14` | 名前の個数 (u8) | 1 | 1 |
| `+0x16` | u16 配列の先頭値＝要素数 | 2 | **32** |
| `+0x18..` | u16 配列 | `2, 0, 101, …` | `32, 0, 101, …` |
| `+0x28..` | **頂点レコード**（**36 B = 0x24**） | – | – |
| 末尾付近 | 4 文字名（16 B 間隔） | – | – |

**頂点レコードの実測（`11\18` `fire` 0x110 B）** — `80 80 80 80`（色マーカー）の位置から確定:

```
色マーカーの位置: 0x46, 0x6A, 0x8E, 0xB2, 0xD6, 0xFA   → 間隔 0x24（36 B）、6 頂点
レコード先頭 = 0x36 + i*0x24 、色は +0x10
0x36 + 6*0x24 = 0x10E ≒ チャンク末尾（0x110）
```

| レコード内 | 内容 |
|---|---|
| `+0x00` | float3 位置（x, y, z） |
| `+0x0C` | float（法線 or W） |
| `+0x10` | **D3DCOLOR**（実測 `80 80 80 80`＝中立） |
| `+0x14` / `+0x18` | float u, v |
| `+0x1C` / `+0x20` | 未確定（8 B） |

→ **`0x1F` は 36 B 頂点 × 6（=1 クワッド）の静的メッシュ**。`0x21`（24 B 頂点）と対になる。
　 `+0x16 = 2` は「形状（クワッド）数」と解釈できる（`f101` は 32）。

### 10.1 当方への含意

- 現在 `0x1F` を**一切描画していない**（`--selftest` の `frm=0(none)` が該当）
- 参照動画の「煙の塊」は `0x1F` のメッシュである可能性が高い
  （`0x21` は板ポリ、`0x1F` は形状付き）
- 実装方針: `0x1F` を `+0x16/0x18` の u16 列をインデックスとして三角形化し、
  **頂点を 24 B で読む**（`0x21` と同じパーサ）。テクスチャは末尾の 4 文字名で解決

### 10.2 実測で分かった訂正（重要）

`fire`(0x110)/`f101`(0xDB0) の実サイズから検算すると、**「頂点数 = `+0x16` の値」**が正しい
（`shapes * 6` では収まらない）:

| チャンク | `+0x16` | size | `0x36 + n*0x24` | 判定 |
|---|---|---|---|---|
| `fire` (11\18) | 2 | 0x110 | 0x36+0x48 = 0x7E | ✓ 収まる |
| `f101` (11\17) | 32 | 0xDB0 | 0x36+0x480 = 0x4B6 | ✓ 収まる |

→ 実装（`ParseGeometry`）は `0x36 + i*0x24` を `+0x16` 個読む方式に修正済み。
　 ただし `fa04` では UV が退化（u0 == u1 = 0.984）したため、退化時は (0,0,1,1) に
　 フォールバックするガードを入れてある。

### 10.3 `0x1F` のテクスチャ名（解決済み）

`FUN_0040b9d0` の名前走査を**そのまま再現**して確定した:

```c
// 1) u16 配列 (+0x18, count 個) を読み終えた位置から 4 バイト境界へ
q = align4(0x18 + count*2);
// 2) 2 バイトずつ進め、2 バイトとも印字可能 (0x1F < b < 0x7F) な位置を探す
while (!(printable(q) && printable(q+1))) q += 2;
// 3) 以降 16 バイト間隔で names 個の「4 文字名」を読む（FUN_004059a0 で解決）
for (i = 0; i < names; ++i) name_i = *(u32 *)(q + i*16);
```

実測（`11\18` の `fire`）:

```
0x1F 'fire' size=0x110 names=1 count=2
  scan start=0x1C  firstPrintable=0x1E
  name[0] @+0x1E 4ch='fire' 8ch='fire1   '
```

→ 名前は **4 文字**（8 文字ではない）。`align4(0x18 + count*2)` から 2 バイト刻みで
　 最初の印字可能位置を探すのが要点。

実装（`ParseGeometry`）に反映済み。`12\43` では `geo=1` かつテクスチャ解決済みとなった例がある:

```
[shot] inst g000 subs=1 … tex=1 link=ds12 uv=(0.016,0.016,0.984,0.984) geo=1 srv=000002086AAA6AC0
[shot] inst g003 subs=1 … tex=4 link=ds15 uv=(0.000,0.000,1.000,1.000) geo=1 srv=000002086AAA7680
```

### 10.5 頂点は half-float（確定）と地面平面

実測（`11\18` の `fire`）で **位置は 16bit half-float** と確定:

```
0x30: 00 3F 00 00 00 BF ...  → half 0x3F00 = 1.75, 0xBF00 = −1.75
v0=(1.75, 0, −1.75) v1=(1.75, 0, 1.75) v2=(−1.75, 0, −1.75) …
→ Y=0 の XZ 平面（3.5 m × 3.5 m の地面クワッド）
```

- レイアウト: 開始 `0x30`、stride `0x24`、頂点数 = `+0x16 * 3`、位置 `+0x00/+0x02/+0x04`（half）、
  色 `+0x16`（D3DCOLOR）、UV `+0x1A` / `+0x1E`（float）
- `f101`（size 0xDB0, count=32）で `0x30 + 96*0x24 = 0xDB0` が**末尾一致** ✓

→ 実装（`ParseGeometry`）はこの形式に更新済み。Y がほぼ 0 で XZ に広がる場合は
　 `geoFlat`（地面デカール）と判定し、`--geoflat on` で世界軸（X/Z）描画になる。

### 10.4 既定は `--geo off`（理由）

`0x1F` の bbox を寸法に使うと `11\22` が 5,686 → **11,545**（地面平面として描くと 6,796）と変化する。
地面クワッドは**本来カメラ正対ではない**ため、ビルボード経路に混ぜると破綻しやすい。
また未解析領域を頂点として読むと Y が 950 m 等の異常値になるため、
**妥当性ガード（各軸 0.01〜20 m、座標 ±100 m）**を入れて弾いている。

### 10.5b レイアウト検算（AltanaView の名前走査と突き合わせ）

`FUN_0040b9d0` の走査（u16 配列の後を 4 B 境界に揃え、2 B 刻みで印字可能位置を探し、
以降 16 B 間隔で 4 文字名）を実データに適用した結果:

| チャンク | `+0x16` | u16 末尾 | 名前位置 | 頂点開始 `0x30` + `count*3`×0x24 | 終端 |
|---|---|---|---|---|---|
| `fire`（11\18, 0x110） | 2 | 0x1C | **0x1E = 'fire'** | 0x30 + 6*0x24 = **0x108** | 0x110（8 B 余り） |
| `f101`（11\17, 0xDB0） | 32 | 0x58 | 0x62（誤検出 'rt..'） | 0x30 + 96*0x24 = **0xDB0** | 0xDB0（**完全一致**） |

- **`count*3` 本を 0x30 から読むと `f101` はチャンク末尾に一致**、`fire` も 8 バイト余りで整合
- 一方 `fire` の名前は **頂点より前（0x1E）** にあり、`f101` では 0x62（頂点領域内）に誤検出される
  → **名前ブロックの位置は「頂点の前」と「後」が混在**している可能性があり、未確定

**現行実装**: 頂点は `0x30` から `count*3` 本（チャンクサイズで上限化）とし、
**6 頂点ごとのクワッド単位で妥当性判定**（±100 m・20 m 上限）。
`fire`/`f101` の終端一致から、この解釈を採用している。

### 10.5c ヘッダ確定（実測 3 例の比較で判明）

`fire`（11\18）と `f101`（11\17）と `ic`（11\22）のヘッダを並べると、レイアウトは **0x30 バイト固定**で一致した:

```
0x00 4B  名前（'fire' / 'f101' / 'ic'）
0x04 4B  サイズ/型ワード
0x14 u8  名前数（=1）
0x16 u16 三角形数（fire=2, f101=32, ic=30）
0x18 u32 同上（冗長）
0x1C u16 101（共通値）
0x1E 8B  グループ名   "fire1   " / "firef1  " / "ice1    "
0x26 8B  別名         "fire16  " / "f10f    " / "ice2    "
0x2E 2B  （0 または端数）
0x30     ★頂点（36 B × 三角形数×3）
```

- **頂点開始は 0x30 で確定**（`f101`: `0x30 + 96*0x24 = 0xDB0` がチャンク末尾に一致、
  `fire`: 0x108（8 B 余り）、`ic`: 0xCD8（8 B 余り）で一貫）
- `0x1E` の 8 文字は **`0x20` テクスチャ名の前半 8 文字（グループ名）と一致**する
  - `0x1F 'fire'` = "fire1   " + "fire16  " / `0x20` = "fire1   fire15  " → 前半一致
  - `0x1F 'ic'`   = "ice1    " + "ice2    " / `0x20` = "ice1    ft3js   " → 前半一致
- 後半 8 文字は一致しないため、**テクスチャ解決はグループ名（先頭 8 文字）で行う**
  → `FindTextureIndexByGroup()` を追加。`ic00..ic03` が tex=3（ice1）に解決した

### 10.5d 頂点レコード（36 B）のフィールド確定

`fire`（y が全頂点 0 の平面）を基準に、18 個の half を全部書き出して同定した:

| オフセット | 型 | 内容 | `fire` v0 の実測値 |
|---|---|---|---|
| +0x00 | half | **x** | 1.75 |
| +0x02 | half | **y** | 0 |
| +0x04 | half | **z** | -1.75 |
| +0x06..+0x12 | – | 未使用/0（`f101` では非 0 の残骸あり） | 0 |
| +0x14 | half | UV スケール相当（1.875 / -1.87） | 1.875 |
| +0x16/+0x18 | half | ≈0 | -7.6e-6 |
| +0x1A | half | 0 | 0 |
| **+0x1C** | **half** | **u** | 1.871 |
| +0x1E | half | 0 | 0 |
| **+0x20** | **half** | **v** | 0 |
| +0x22 | half | 0 | 0 |

`fire` の 4 隅は `(u,v) = (1.871,0) / (1.871,1.871) / (0,0) / (0,1.871)` で完全に整合する。

- **旧実装の誤り**: UV を `+0x1A/+0x1E` から **float32** で読んでいた → 実際は half で
  `+0x1C/+0x20`。このため全 UV が 0 になり、1 テクセルだけを引き伸ばしていた。

### 10.5h `+0x02 y` の異常値は「未初期化成分」（285 チャンク実測）

`ROM\11\0.DAT`〜`11\39.DAT` の **0x1F 285 チャンク**を走査した結果:

| チャンク | 頂点数 | \|y\|<1 | <10 | <100 | **≧100（異常）** | 異常率 |
|---|---|---|---|---|---|---|
| `fire`（11\18） | 6 | 6 | 0 | 0 | **0** | 0% |
| `ic`（11\22） | 90 | 39 | 29 | 6 | **16** | 18% |
| `syur`（11\0） | 144 | 28 | 12 | 14 | **90** | **63%** |
| `m1`（11\3） | 12 | 2 | 0 | 0 | **10** | 83% |

- 異常値は **常に 1 軸だけ**に偏る（例: `syur` は y のみ、`r0` は x のみ）。
  値は 457 / 1882 / 6.1e4 のように「意味のない大きさ」で、**未初期化バイト**と判断
- したがって `y` は「書かれていれば実座標（例: `m2` は max|y|=7.68 で 0% 異常）」、
  「書かれていなければ無効」の 2 状態

**実装した規則（Effect.cpp `ParseGeometry`）**

1. チャンク全体で軸ごとに `|v| ≧ 100` の割合を数え、**30% を超えた軸は無効**（0 固定）
   - `syur` 63% → y 無効 → XZ 平面として描く（`syu0 half=(4.867, 0.000)`）
   - `ic` 18% → y 有効 → 氷柱として描く（`half=(3.443, 19.600)`）
2. 無効でない軸でもクワッド単位に異常値が残るため、**同じクワッドの有効値の中央値**で補う
3. 平行四辺形の辺長が 50 m を超えるクワッドのみ捨てる（旧: 全体 bbox 依存で過剰に破棄）

この結果 `ic` の有効クワッドは **9 → 15（全数）**、`syur` は 24/24 が描画対象になった。

> なお `+0x14` は **UV レンジ相当の定数**（`fire`=1.875、285 チャンク中 186 で
> `max(u,v)` と 0.02 以内で一致）。UV をこの値で正規化しても差は 0.2% 程度なので
> **生値のまま**使う（`+0x14` の意味は「UV スケール」と記録するに留める）。

### 10.5e 描画: ビルボードではなく実 3D 平行四辺形

`0x1F` は実頂点を持つため、カメラ正対の軸（`axR`/`axU`）に `half` を掛ける方式をやめ、
**A=v0, B=v1, C=v2 から平行四辺形を作って 3D のまま描く**方式にした。

```
aR = (B - A) / 2,  aU = (C - A) / 2,  ctr = A + aR + aU
uv = (A.u, A.v) .. (B.u + C.u - A.u, B.v + C.v - A.v)   // 対角 A' = B + C - A
```

- インスタンス行列 `M` は位置 `w=1` / 辺ベクトル `w=0`（`XMVector3TransformNormal`）で適用
- **インスタンスの Scale（`s[0..2]`）は掛けない**: 0x1F の頂点は実寸（m）で持っており、
  ビルボードのサイズは `0x21` の実寸で決まるため（`--size meter`）。
  Scale を掛けると `0x0F`（Scale 設定）で氷柱が 1/4 に萎む → 掛けない方式に修正

### 10.5i α の扱いと `--geo on` の空白（未解決事項の切り分け）

- ビルボード側は `rgba[3] <= 0` のとき **α を 1 に強制**している（「VM が色を
  書いていない generator の代替」）。このため **全粒子 α=0 の時間帯でも絵が出る**
- `--geo on` は α を尊重するので、その時間帯は**空白**になる
  （実測: `11\27` / `11\28` の frame 30。既定は 973 / 1,437 px だが、
   ログでは全インスタンス `col=(…,0.00)`）
- これは「α=1 強制」が過剰である可能性を示す。切り分けには
  **色を書いたか（`0x16`/`0x17`/`0x18` 実行済みか）のフラグ**が必要で、
  既定の絵が広く変わるため**設計変更として扱う**（今回は実装しない）

### 10.10 参照動画との差の正体（2026-11-09 計測）

`fire2.mp4`（`11\18` Fire II）との差分を「炎領域の bbox 縦横比」で測った:

| 画像 | 炎ピクセル | bbox | **縦横比 (w/h)** |
|---|---|---|---|

| 当方 `--frames 180`（**`--layout on`** = 旧既定） | 1.33% | 472×232 | **2.03（横帯）** |
| 当方 `--frames 180`（**`--layout off`** = 新既定） | 1.33% | 176×232 | **0.76（縦）** |

**原因 1（修正済み）: デバッグ用の横並びが既定で有効だった**

`g_Layout`（位置が 0 のインスタンスを横 1.6 m 間隔で並べる確認用機能）が
既定 `true` だったため、位置を計算できていないインスタンスが横一列に並び、
参照の「縦に伸びる火柱」ではなく「横長の帯」になっていた。
→ **既定を `off` に変更**し、`--layout on|off` で切り替え可能にした。

**原因 2（未実装・本命）: 連続放出（パーティクル・プール）が無い**

当方は `MotionInstance::Reset` で `count+1` 個のサブを **t=0 で同一初期化**し、
以後ずっと同じ寿命で回す。AltanaView は**時間をかけて粒子を追加生成**し、
寿命で消す（`FUN_0040e0b0` / `FUN_00410090`）。

```
FUN_0040e0b0（毎フレーム）
  既存粒子ごと:  VM#2(dt)
                返り値 0（寿命）→ FUN_00410090（再初期化）
                                    ctx[0x5e]==0 なら粒子を削除（memmove で詰める）
  ctx[0x50] -= dt                                  // 放出タイマ
  while (ctx[0x58] <= ctx[0x50]) {                 // 次の放出時刻に達したら
      粒子配列を ctx[0x4c] 個ぶん拡張（0 埋め）
      for k in 0..ctx[0x4c]:
          FUN_0040e650(ctx, 粒子, 前回放出からの経過)   // ★VM#1 で初期化
      ctx[0x58] -= ctx[0x54]                        // 間隔を進める
  }

FUN_00410090（粒子の再初期化）
  elapsed(0x3b)=0, T01(0x3c)=0
  Move(0x23..0x25) -= rand()*2π        // 位相のランダム化（C58 = 2π）
  UV(0x2d,0x2e)    -= rand()
  キーフレームポインタ（op 0x20..0x37/0x58..0x5b の dest+0x43）= 命令の arg2
  VM#2(dt = 寿命超過分)                 // 端数を繰り越す
```

関連フィールド（実測）:

| ctx | 内容 | 由来 |
|---|---|---|

| `+0x4c` | 1 回の放出粒子数 | 未特定（ジェネレータ設定由来） |
| `+0x54` | 放出間隔（秒） | 未特定 |

### 10.12 op `0x06` を確定実装（定数は 65536 前割り）

逆アセンブル（`0x40E9B0`〜`0x40EA00`）で実命令を確認した:

```
DC 05 30 2C 45 00   fadd  qword [0x452C30]   ; +2^30（int→double 補正）
DC 0D 38 2C 45 00   fmul  qword [0x452C38]   ; × 1/65536   ← rand 正規化
DC 0D 70 2C 45 00   fmul  qword [0x452C70]   ; × 2π/65536  → φ
DC 0D 68 2C 45 00   fmul  qword [0x452C68]   ; × π/65536   → θ
DC 25 60 2C 45 00   fsub  qword [0x452C60]   ; − π/2
```

定数の実値（double）:

| VA | 値 | ×65536 |
|---|---|---|
| `0x452C60` | 1.5707963705062866 | — （π/2） |
| `0x452C68` | 7.3145905998828198e-10 | **4.7936901e-05 = π/65536** |
| `0x452C70` | 1.462918119976564e-09 | **9.58738019e-05 = 2π/65536** |

→ **`rand()` は 0..65535 の整数**を返し、定数はあらかじめ 65536 で割ってある。
よって op `0x06` は **一様な球面分布**:

```
mag   = arg1 + arg0 * (rand/65536)
phi   = rand * 2π/65536        (0..2π)
theta = rand * π/65536 − π/2   (−π/2..+π/2)
pos  += (cosθ·cosφ, sinθ, cosθ·sinφ) * mag
```

生成時（VM#1）に 1 回実行されるため、**粒子ごとの初期位置のばらつき**になる。
実装済み（`EffectVm.cpp` case 0x06）。計測（`--frames 90`）:

|---|---|---|
| `11\17` | 4,491 | **5,023** |
| `11\18` | 3,051 | 3,051（この DAT の `0x06` は arg が 0 近い） |

- 色マーカー `80 80 80 80` の実測（`fire`）: 0x46, 0x6A, 0x8E, 0xB2, 0xD6, 0xFA（間隔 0x24、6 個）
- `f101`（size 0xDB0, count=32）で `0x30 + 32*3*0x24 = 0xDB0` が**ちょうど末尾**になる
  → **頂点 = `count*3`（三角形数 × 3）、開始 0x30、stride 0x24** が有力
- 当方は暫定で `0x36 + count*0x24` を使用中（テクスチャ未解決でも描画に影響しない範囲）
  → 上記の説に合わせて**次回修正**する
- `ma*?`/`mb*?`/`mi*?` などは **モデル内の 0x2B（モーション）チャンク**（実測: `ma00`,`ma10`,`ma20`）
- `st*`/`ss*`/`ne*`/`ei*` などは **別 DAT（base `0\0.DAT` 等）の名前**と推定
- 効果 DAT の `mdam`/`proc` も**自 DAT には無い** → 相互参照は「同一 DAT → base」の順で解決されている

## 12. 寿命の基準は「エフェクト継続時間」（AltanaView 実測）

`op 0x01` の `LifeTime`（`+0x22`）は**サブの存在期間には使われていない**ことを確認した。

### 12.1 根拠（`FUN_0040f4b0` = VM#2）

```c
fVar5 = param_3 + sub[0x3b];                       // dt + 経過時間
if (*(float *)(param_1 + 0x1c8) == 0.0f || fVar5 < *(float *)(param_1 + 0x1c8)) {
    ret = 1;  t01 = fVar5 / *(float *)(param_1 + 0x1c8);      // ★+0x1c8 = エフェクト継続時間
} else {
    ret = 0;  t01 = 1.0f;                                     // 寿命終了
    dt = *(float *)(param_1 + 0x1c8) - sub[0x3b];             // 残り時間にクランプ
}
```

- 参照しているのは **`ctx+0x1c8`（エフェクト全体の継続時間）** のみ
- `sub[0x54]`（生成物の長さ = `(u16@+0x76+1)/60`）は**寿命判定に使われていない**
  （`+0x54` の参照は別オブジェクト＝タイムラインの間隔 `this+0x50/0x54/0x58`）
- `+0x1c8` の設定元（`FUN_0040d790` 11026-11031）は
  `u32@(ip+0x20)` の **下位 8bit = サブ数 / 上位 16bit = 継続時間[フレーム]** で、
  `+0x1c8 = frames/60`

### 12.2 含意

| 項目 | AltanaView | 当方 |
|---|---|---|
| サブの存在期間 | **エフェクト継続時間**（`+0x1c8`） | 既定で `ctx.Duration()`（**一致**） |
| `LifeTime`（op01 `+0x22`） | 存在期間には**未使用** | `--life on` で使用（**非忠実**） |
| 生成物の長さ（`+0x76`） | 存在期間には**未使用** | 未使用（`--life` は op01 を参照） |

→ **`--life` は AltanaView の挙動ではない**ため、既定 off のまま
　 「実験用（寿命を短くするとどうなるか）」として残す。

### 12.3 `--geoflat` の適用範囲を拡張（今回）

`bil == 0`（データ由来の平面）なら `0x1F` が無くても世界軸（XZ）で描くようにした。

| 条件（`11\22` / 90 フレーム / `--bg 40F0F0`） | 非背景 |
|---|---|

### 11.2 データ2 op 0x01（48 B）— 当方で実測一致

### 11.5 ★最重要: アタッチ先は「列挙された体の部位」

ページには `+0x04/06` のフラグ値ごとに**体の部位**が列挙されている（要約）:

```
0x001/0x011 中心, 0x031 非中心, 0x041 胴前面, 0x071 手前,
0x081 右腕(少し), 0x091 左腕(少し), 0x0A1 右足, 0x0B1 左足,
0x0C1 頭(少し上), 0x0D1/0x0E1/0x0F1 右腕・左腕の各位置,
0x101 右足, 0x111 足, 0x121 左足, 0x131 左足(少し上),
0x141 右足との距離, 0x201 右手前(指定ほど前)
```

- 値は `0x001 + n*0x10` の形（＝下位 4 bit が形式、上位が**部位番号**）
- これは `FUN_0040d790` の `bone = (u & 3) == 1 ? u >> 4 : u >> 10` と**完全に整合**
- つまり **bone index ではなく「アタッチ部位 ID（0〜0x14, 0x20）」**。

→ 参照動画の「腕・脚・胴に炎」は、この**部位 ID** を骨に対応づけて実現されている。
　 当方の `--bone-map`（手動/auto）は、この部位 ID 表を**モデルの骨順に対応づける**ことで
　 データ駆動に置き換えられる見込み（骨名が無いため、部位→骨の対応表を別途用意する必要がある）。

- モデル側スケジュールには **`(a,b)` の id と名前**しか無く、**bone index は見当たらない**
- したがって「粒子 → 骨」の対応は、`FUN_0040d790` に渡される**別種のチャンク**
  （未特定。§8.2）か、**アプリ側の固定規則**（例: 効果ごとに既定の骨）である可能性が高い
- 当方の当面の運用は `--bone-map`（§7.3）で近似するのが妥当

- `+0x1a0 == 0`（単体再生）: **ルート行列をコピーし、VM#1 の op を全部実行**
- `+0x1a0 != 0`（モデル/ボーン従属）: **VM#1 の op を実行しない**（位置は骨行列側で決まる）

→ 参照動画（キャラに付いた Fire II）は `+0x1a0 != 0` の経路。
　このため粒子位置は骨（体）付近に固定され、`0x02`/`0x47` による**位置の流れが発生しない**。

**当方への含意**:
- 単体再生（`--shot <dat>`）では VM#1 の位置 op が走るため、粒子が Z 方向へ流れる（実測 `z=-1〜-9`）
- 参照動画と同じ絵にするには **モデル従属モード**（`--bone` 相当）で VM#1 の位置 op を
  **スキップ**する必要がある（`+0x1a0 != 0` の再現）
| 項目 | 実装 |
|---|---|
| 経過時間 | 折返しをやめ、`t>=dur` で `t=dur`・`t01=1`・`ended=true` |
| 寿命 | `ended` かつループフラグ無し → インスタンス終了（従来どおり） |
| ループフラグ | `EffectContext::m_LoopRespawn`。**main（0x07）のストリーム D（+0x8C）に op 0x05** で立つ（`FUN_0040d790`） |
| 再初期化 | ループ時は経過時間 0・Move を `byteRand/60` ずらす・UV オフセットを `byteRand` ずらす |
| `byteRand` | `RandByte()` = `(int)(Rand01()*256) & 0xFF` |

実測（`11\17`/`11\18`/`11\22`/`12\43`）では main の `+0x8C` が空 or `0x6D 0x07` のため
**ループフラグは立たず**、ゴールデンは不変（8,050 / 2,694 / 7,317 / 10,729）。

### 5.5 UV オフセット（実装済み・既定オフ）

`0x27`/`0x28` → スロット `0x2D/0x2E`（= `0xB4/0xB8`）への `k * arg[0]` 累積を実装し、
描画時に **0..1 を巡回**させて適用できるようにした（`--uvscroll`）。

| モード | 挙動 |
|---|---|
| `off`（既定） | オフセットを適用しない |
| `on` | 累積値を `frac` して 0..1 を巡回（ユーザー指示の解釈） |
| `cell` | アトラスの 1 セル幅で巡回（比較用） |

実測（`11\18` / 180 フレーム / `--bg 40F0F0`）: `off` = 3,296 → `on` = **3,034**、`cell` = **3,034**（同値）。
`11\17`・`12\43` はオフセットが 0 のため不変。

> **注意**: 既定を `off` にしているのは、巡回させると別セルをサンプリングして見た目が崩れるため。
> 累積値・巡回の実装自体は指示どおり入れてあり、フラグで切替できる。

### 5.6 帯状アーティファクトの原因（特定済み）

**原因は `scl`（VM が書く 3D スケール）の X 成分膨張**。実測（`11\18` / 90 フレーム）:

```
[shot] inst g006 subs=1 pos=(0.05,-0.10,-1.00) scl=(4.26,1.05,1.03) … uv=(0.500,0.500,0.742,0.746)
```

- 幅 4.26 m × 高さ 1.05 m の**横長クワッド**になり、これが「帯」として見える
- 同様の値が `g004`=`(7.60,1.00,1.03)`、`12\43` の `g006`=`(4.26,…)` でも観測されている
- `--size quad`（`0x21` のクワッド実寸のみ使用）にすると**帯が消える**ことを確認済み
  （`11\18` 180 フレーム: 暗部 4,388／非背景 8,986）

> なお `0x21` を持たないジェネレータ（`hit6`=`f10f` 256×32、`dist`、`hi17` 等）は
> `srv=null` か全面 UV になるが、`srv=null` のインスタンスは描画から除外するようにした
> （黒クワッド化の防止）。

### 5.7 テクスチャ側の実測（`--uvcrop` / `--blend auto` の検証結果）

- **全テクスチャで `uvb=(0,0,1,1)`・`black=0.000`**
  → アルファ 0 の領域も暗部（RGB 和 < 96）も存在しない（パレットは不透明色のみ）
- したがって「黒背景を透明扱いする」ヒューリスティックは成立しない
- 帯はテクスチャではなく **クワッドの縦横比（`scl`）** の問題だった

→ 追加したフラグ `--uvcrop on`（不透明領域で UV を切る）と `--blend auto`（黒割合で
　 alpha/add を選ぶ）は、現データでは**効果なし**（将来の素材向けに残す）。

複数サブは実装済みだが、`12\43` では**全サブが同じ位置**になる（`--trace` で確認:
`inst 2 subN=4 pos0=(1.22,0,-6.10) pos1=(1.22,0,-6.10)`）。AltanaView は次の 2 経路でばらけさせる:

1. **VM#1 の乱数レンジ加算**（op `0x0A`/`0x10`/`0x11`）— `rand*(max-min)+min`。
   当該 generator（`12\43 g011`）の VM#1 は `op=0x11 len=2` が 1 個のみで、
   **引数が float ではなく整数**（`0x14`=20 → float としては 1.4e-42 に見える）。
   範囲の実体は `ctx+0x12C..` 側にある可能性が高い（op `0x47` がそこを加算している）。
2. **毎フレームのジッタ**（`FUN_00410090`）— ルートのフラグ `+0x5e`（タイムライン op `0x05` で立つ）が
   有効なとき、`sub[0x23..0x25] -= rand * 定数` を**サブごとに**適用する。

→ 次の実装は「`0x11` の引数を整数として読み、`ctx+0x12C..` の範囲で `rand` 加算」＋
「`+0x5e` ジッタ」。これで `12\43` の粒子が散る。
