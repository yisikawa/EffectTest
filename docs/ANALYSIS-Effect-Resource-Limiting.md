# エフェクト表示に必要な motion / texture の限定可能性 — 解析レポート

> 日付: 2026-11-09 / 対象: `AltanaView_unpacked.exe`（SHA-256 `b5494a7c…cfae90`, 418,816 B, x86 PE, **D3D9**）
> 実データ: FFXI `ROM\0\0.DAT`（base）＋ `ROM\10\9`, `10\10`, `11\17`, `11\18`, `11\22`, `12\10`, `12\43`, `13\9`, `13\10`, `15\89`, `15\91`
> 手法: 既存解析（`AltanaView-master\_rea\EFFECT_MOTION_ANALYSIS.md`）＋ 擬似 C 11 本 ＋ 実 DAT の機械走査（使い捨てスクリプト `%TEMP%\av_eff2\*.ps1`）
> 制約: 本レポートは解析のみ。アプリのコードは変更していない。

## 1. 結論

> **エフェクト Schedule 全体の棚卸し（3,196 件の走査結果）は設計書 §4.9 に記載**（25 カテゴリ、`0x07` の 81.4% が複数、尺・資源規模の分布、代表ゴールデン）。本書は資源限定の可否と `0x19`/`0x21`/`dist`/`nulp` の意味に焦点を当てる。

| 対象 | 限定できるか | 根拠 | 削減余地（実測・直接参照ベース） |
|---|---|---|---|
| **motion（`0x05` generator）** | **できる**（実行時に名前で解決） | AltanaView は「名前 → チャンク表を線形探索 → `type == 0x05` を採用」で生成（`FUN_0040d790` の `(*piVar9 == name) && ((piVar9[1] & 0x7f) == 5)`） | 効果 DAT 内では **ほぼ 0**（タイムラインが全 generator を参照）。**base の 320 個を全索引する必要はない**（参照名だけ解決すればよい） |
| **texture（`0x20`）** | **できる**（generator の `+0xAC` リンク名で辿る） | 全 generator の **+0xAC に 4 バイトのリンク名**。その約半数が `0x20` を指す（`g000→fai1`, `g004→fai0`, `g002→fai2` …） | 直接参照で **3/5・3/7・2/6**（不要 ≥ 2/5・4/7・4/6）。`0x1F`/`0x21`/`0x19` 経由で増えるため、これは**削減可能量の上限** |

**限定の実現に必須な前提が 2 つ、現行実装と食い違っています（§4）。**

## 2. motion を限定できる根拠

- AltanaView のタイムライン実行（`FUN_004103d0`）は `op=0x02` で `FUN_00405900(name)` により**名前からチャンクを解決**し、`FUN_0040d730` で MotionObject を生成する。生成されたものだけが子リストに入り毎フレーム更新される（`FUN_0040e600`）。
- `FUN_0040d790`（擬似 C 281/358/372 行付近）でも、命令中の 4 バイト名を **チャンク配列の線形探索**で引き、`type & 0x7F == 5` のときだけ採用している。
- したがって「タイムラインが名前で呼ばない generator は生成されない」＝**必要分だけ構築できる**。

### 実測（正しく解析できた DAT）

| DAT | 命令数 | generator 参照/総数 | 未参照 |
|---|---|---|---|
| `11\17` Fire | 18 | **8 / 8** | なし |
| `11\18` Fire II | 20 | **11 / 11** | なし |
| `11\22` Blizzard | 18 | **14 / 14** | なし |

→ **効果 DAT 内での motion 削減はほぼ見込めない**（どの DAT も全 generator を使う）。
一方、現行 `EffectBase` は base の **320 generator を全部索引**しており、ここは「参照名だけ解決」に変えられる（`mdam` / `proc` / `mprc` のような共有タイムライン名だけが実際に引かれる）。

## 3. texture を限定できる根拠

### 3.1 紐づけは generator ヘッダ +0xAC の固定フィールド

```
gen=g000 tex=fai1 rel=+0xAC        (11\17)
gen=g001 tex=fai0 rel=+0xAC
gen=g002 tex=fai2 rel=+0xAC
gen=g004 tex=fai0 rel=+0xAC
gen=un00 tex=un   rel=+0xAC        (12\10)
gen=tm00 tex=tm   rel=+0xAC        (12\10)
gen=g000 tex=bers rel=+0xAC        (15\89)
gen=g005 tex=ber2 rel=+0xAC        (15\89)
```
- **`+0xAC` はテクスチャ専用ではなく「リンク名」**。参照先の型は相手次第で、実測では次の 5 種に分かれた。

| 参照先 | 例（11\17 / 11\18 / 11\22） | 意味 |
|---|---|---|
| `0x20`（同 DAT） | `fai0`, `fai1`, `fai2`, `fire`, `fir3`, `pka1`, `kem2` | **テクスチャ**（描画に直接必要） |
| `0x1F` | `fa04`, `ic  `, `pkm2`, `ft32`, `giz3` | ジオメトリ／パラメータ束（現行スコープ外） |
| `0x21` | `kir1`, `fai0` | テクスチャ付随ブロック（UV/フレーム等。要確認） |
| `0x3D` | `3032`, `3033` | 条件／パラメータブロック |
| base のみ | `hit6`, `hi17` | **base の `0x20` に実在**（共有テクスチャ） |
| `dist` / `nulp` | `dist`, `nulp` | `dist` は**予約語**（距離ベース）、`nulp` は**参照先なし**（§7 で確定） |

- 名前は**型を跨いで衝突**する（`hit1` は base の `0x05` と `0x20` の両方に存在）。解決時は型を明示する（AltanaView も `& 0x7f` を検査）。

### 3.2 実測（`+0xAC` の直接参照）

| DAT | `0x20`（ローカル） | base の `0x20` | `0x1F`/`0x21`/`0x3D` 経由 | ローカル `0x20` 総数 | 直接参照されない |
|---|---|---|---|---|---|
| `11\17` Fire | `fai0`, `fai1`, `fai2`（3） | `hit6`, `hi17`（2） | `fa04`(0x1F) / `3032`(0x3D) | 5 | `fai3`, `f101` |
| `11\18` Fire II | `fire`, `fir2`, `fir3`（3） | `hi17`（1） | `3033`(0x3D) | 7 | `fir1`, `fir4`, `fir5`, `kemu` |
| `11\22` Blizzard | `pka1`, `kem2`（2） | なし | `ic`/`pkm2`/`ft32`/`giz3`(0x1F), `kir1`(0x21) | 6 | `pke1`, `giz1`, `ft31` |

- `0x1F`/`0x21` を辿ると必要数は増える。例: Blizzard の `ice1` は `0x1F`(`ic`) 経由で必要。`fai3` / `fir5` / `kemu` / `pke1` などは**どの経路からも参照が見つからない**。
- `0x21` は現行スコープで扱わないため、`fir1`/`fir4` は「不要」に分類した（扱うなら必要になる）。
- 現行スコープでは `0x1F`（ジオメトリ）を描画しない（設計 §1 スコープ外）ため、`0x1F` 経由のテクスチャは**現時点では不要**と判断できる。

### 3.3 base（`ROM\0\0.DAT`）の規模

| 項目 | 値 |
|---|---|
| チャンク | 1,105 |
| `0x05` generator | **320**（`+0xAC` の異なり 91 種のうち **45 種が base の `0x20` 名**） |
| `0x20` texture | **61**（`plig`, `spec`, `test`, `hit1`〜`hit9`, `eis1`〜`eis4`, `ei30`…, `asi1`, `h260`, `fmk1` …） |
| 効果から実際に引かれる共有名（例） | `mdam` / `proc` / `mprc`（`0x07`）、`hit1`（`0x1F`／効果により異なる） |

→ base は「共有ライブラリ」であり、**全 320 generator・全 61 texture を起動時に構築する必要はない**（必要な名前だけ遅延解決）。

## 4. 現行実装との食い違い（限定の前提条件）

| # | 事実 | 現行実装 | 影響 |
|---|---|---|---|
| **A** | `main` の命令列開始は **固定ではない**（実測 `+0x74` / `+0x80` / `+0xA0`） | `memcmp(name,"main")==0` なら **+0x80 固定**（`Effect.cpp:134-137`） | **`11\18`・`11\22` は 0 命令**（＝表示できない）。限定集合も算出不能 |
| **B** | texture は generator の **+0xAC リンク名**（`0x20` を指す場合）で決まる | `Spawn()` が **`texIndex = 0` 固定**（`Effect.cpp:288`） | 見た目が全 generator で同一テクスチャ。限定以前に**割当が未実装** |
| C | 名前解決は型付き（`&0x7f`） | `Find(name4, type)` で型指定あり（`Dat.cpp:66`） | 問題なし（踏襲） |

## 5. 限定を実装する場合の方式（設計への反映案）

1. **タイムライン開始の自動判定**（A の修正）
   - 候補オフセットを 4 バイト刻みで走査し、「末尾が `len==0` で終わる」「`op` が既知集合」「名前参照 op の名前が DAT（または base）に解決できる」を満たす**最長**候補を採用。
   - 実測 3 件では `0x74`/`0x80`/`0xA0` を正しく判別できた（§2 の命令数と一致）。
2. **texture 割当**（B の修正）: `GeneratorBlock.linkName = chunk[+0xAC]`（4 バイト）を保持し、型 `0x20` に解決できたときだけ `MotionInstance.texIndex` に反映（解決できなければ白テクスチャ）。
3. **必要集合の算出**（本レポートの主題）
   ```
   link(g)  = chunk[g + 0xAC] の 4 バイト名（同 DAT 優先 → base）
   needed05 = { timeline の名前参照 op の名前（型 0x05 で解決） }
              ∪ { base へフォールバックした 0x07 を再帰的に解析した結果 }
   needed20 = { link(g) | g ∈ needed05 かつ link(g) が 0x20 }                      … 直接
              ∪ { 0x19 / 0x1F / 0x21 が参照する 0x20（スコープ内の経路のみ） }        … 間接
   ```
   ※ `link(g)` が `0x1F` / `0x21` / `0x3D` のときは、そのブロックを辿って `0x20` を探す（現行スコープでは `0x1F` を対象外とする）。
4. **遅延ロード**: base は索引のみ（`0x05`/`0x20` を**名前→チャンク**のハッシュに）。`0x20` の SRV 化は**必要になった時点**（初回参照）に行い、LRU で解放。
5. **検証**: アプリに新フラグは足さない。(a) `--selftest` に `prog=`（開始オフセット）と `tex=`（割当）を 1 語ずつ追加、(b) `needed05` / `needed20` は同梱の外部スクリプトで算出し、本レポートの実測値（`11\17`: 8/8 gen, 3/5 tex）をゴールデンにする。

## 7. 追加解析: `0x19` / `0x21` / `0x1F` の意味と `dist` / `nulp`（ModelTest 参照を含む）

> 追加根拠: ModelTest（`Model.cpp:1267`「`0x19` = Info」）／ 擬似 C `FUN_0040d790` の型ディスパッチ ／ 実 DAT のダンプ（`11\17`, `11\22`, `12\10`）／ 全 ROM の base 走査

| 型 | 実体（実測） | 根拠 | 現行スコープでの扱い |
|---|---|---|---|
| `0x19` | **キー（時間, 値）表**。16 B ヘッダ＋ float 列（32 B=4、48 B=8、64 B=12、80 B=16 floats）。例 `k000`: `0.0, 0.0, 1.0, 0.8` | ダンプ ＋ `FUN_0040d790:303`（`(*piVar9 == name) && (&0x7f) == 0x19` で**名前から解決**）／ModelTest も `0x19` を「Info」として読む | **未使用**（現行 VM は generator payload 内 `tblA..tblD` のみ参照。`EffectVm.cpp:27,193`）。**テクスチャではない** |
| `0x21` | **テクスチャ付随（フレーム）ブロック**。内部に 4 B 名の並び（`fai0`, `1   `, `fai02   `）と UV/色らしき値（192–2,416 B） | ダンプ（`fai1`=192 B）＋ `FUN_0040d790:208`（type `0x21` → `FUN_0040c360` でオブジェクト構築） | **スコープ外**（静止テクスチャのみ）。実測では 0x21 を辿っても**新たな `0x20` は要求されない**（内部名 `fai01`/`fai02` はチャンクに存在しない＝フレーム名） |
| `0x1F` | **ジオメトリ（メッシュ）**。`f101.m` 等、272–3,504 B | ダンプ ＋ `FUN_0040d790:188`（type `0x1F` → `FUN_0040b9d0`） | **スコープ外**（設計 §1） |
| `0x3D` | **パラメータブロック**（560–1,728 B） | ダンプ | 未使用（読み飛ばし） |
| 参照型の決まり方 | オブジェクトの **`+0x21` バイト**が参照型。`0x0B→0x1F` / `0x0E→0x21` / `0x1D→0x25` に読み替えてから名前解決する | `FUN_0040d790:149-170` | 実装時に踏襲（型を跨ぐ名前衝突の回避） |
| **`dist`** | **予約語**。`iVar11 == 0x74736964`（= "dist"）で分岐し、チャンクを引かない（距離ベースの扱い） | `FUN_0040d790:156` ＋ バイナリ内リテラルは 1 箇所のみ | **解決不要**（テクスチャもチャンクも要らない） |
| **`nulp`** | **参照先なし**。バイナリにリテラル 0 件、全 ROM の base（`ROM\0`,`10`,`11`,`12`,`13`,`15` の `0.DAT`）とサンプル DAT にチャンク 0 件 | 走査 | **リンク無し**として白テクスチャで代替（R10） |

**必要資源への影響（確定）**
- テクスチャ（`0x20`）を要求するのは **`+0xAC` が `0x20` を指す場合のみ**（＋将来 `0x21` を実装する場合のフレーム解決）。
- `0x19` / `0x3D` / `0x1F` はテクスチャを要求しない。`0x19` は値表なので、VM を拡張する段階で「小さい追加資源」として扱う。
